# swift-cpu

Use this package when you need the processor itself rather than an abstraction over it: an acquire or release load or store on memory you hold by pointer (`CPU.Atomic`), a one-way ready signal between threads (`CPU.Atomic.Flag`), a fence (`CPU.Barrier`), a spin-loop hint (`CPU.Spin`), a cache prefetch or a value isolated on its own cache line (`CPU.Cache.Padded<T>`), a raw counter read for cheap interval measurement (`CPU.Timestamp`), or a CRC-32C checksum (`CPU.Integrity.Cyclic.Castagnoli`). It also names logical processors, cores and NUMA nodes (`CPU.Logical`, `CPU.Core`, `CPU.NUMA`), but never asks the operating system for them: the platform packages (swift-darwin-standard, swift-linux-standard, swift-windows-32, swift-iso-9945) report counts and `CPU.NUMA.State`. For atomics on values you own rather than on foreign memory, use the standard `Synchronization.Atomic`.

## Laws

- `CPU.Atomic.load` and `CPU.Atomic.store` are C11 atomic accesses to the pointee. They order memory only if every concurrent access to that location also goes through them; a plain Swift read or write racing with them is a data race. `.relaxed` gives atomicity only; an `.acquiring` load that sees a `.releasing` store also sees every write made before that store.
- `CPU.Atomic.Flag` only goes from unset to set. `set()` releases and `isSet` acquires, so a thread that observes `isSet == true` sees every write the setting thread made before `set()`.
- `CPU.Barrier.compiler` emits no instruction: it stops the compiler from moving memory accesses across it and orders nothing between threads. `CPU.Barrier.hardware` emits a fence: `full()` orders all accesses, `load()` loads only and `store()` stores only. On 32-bit ARM `load()` and `store()` are full fences. On an architecture other than x86, ARM64 or ARM32 every hardware fence degrades to a compiler barrier, `CPU.Spin.hint()` does nothing and prefetch does nothing.
- `CPU.Cache.prefetch` is a hint: it never changes program results. It targets all cache levels. On x86 under MSVC `write(_:)` is issued as a read prefetch.
- `CPU.Cache.Padded<T>` stores its value in its own heap allocation, aligned to 128 bytes and at least 128 bytes long (larger only when `T`'s stride is). Two padded values never share a 128-byte block. Each instance costs one allocation, freed on deinit.
- `CPU.Integrity.Cyclic.Castagnoli.compute` is CRC-32C (reflected polynomial 0x82F63B78, initial value and final XOR all ones): "123456789" gives 0xE3069283. Passing a previous result as `seed` continues it: the checksum of `a` then `b` with `seed:` set to the checksum of `a` equals the checksum of `a + b`. An empty buffer returns `seed` unchanged. The hardware instruction is chosen at compile time (SSE4.2 on x86 outside MSVC, the CRC extension on ARM64), not detected at run time; without it the table implementation runs, and both give the same result.
- `CPU.Timestamp.read()` returns the raw value of the processor's counter with no conversion: the time-stamp counter on x86, the virtual counter on ARM64 and ARM32. Units and frequency differ by architecture, so subtract two readings from the same machine and never treat the value as time. Reads are not serializing, so the processor may reorder them with neighbouring instructions. Successive reads on one thread do not decrease. On any other architecture the value is always 0.
- With the `BinarySerializer` trait, `CPU.Timestamp` and `CPU.Integrity.Cyclic.Checksum` serialize their raw value in host byte order and append to the buffer rather than replacing it. The bytes are therefore not portable between machines of different endianness.
